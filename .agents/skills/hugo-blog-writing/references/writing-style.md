## 标题和开篇

标题说明“对象 + 讨论的机制或范围”。范围较大时，用副标题列出真正贯穿正文的几部分，不把全部目录塞进标题。

- `后端架构` 太宽；`后端架构演进：服务拆分、环境选路与研发平台建设` 能说明正文范围。
- `我们怎么学会跟着模型往前走` 侧重感想；正文讲具体实现调整时，用 `游戏 Agent 演进之道`，再在开篇交代 Prompt、多 Agent、Skills 等范围。

开篇通常用一两段交代对象的用途、需要解决的问题，以及本文讨论的范围。读者进入正文前不必先读一大段经历和结论。

章节标题优先使用对象、动作或机制，例如“运行记录”“命令执行会话”“环境回退条件”。不要让每个标题都成为长句、口号或设问。

## 选择展开顺序

不同文章使用不同顺序，下面是可选组织方式，不是统一模板。

**实现说明**：对象与接口 → 数据布局 → 操作流程 → 特殊情况。先让读者知道图里的东西是什么，再解释它们如何变化。

**架构对比**：先完整讲清方案 A，再用相同的关键问题讲方案 B，最后比较。表格可以归纳差异，但不能代替两套架构的机制说明。

**演进记录**：每个阶段说明原实现、遇到的具体限制、做出的改动以及随之增加的工作。保留发生顺序，不把所有阶段改写成事后感想。

**故障与恢复**：正常执行 → 在哪一步中断 → 哪些事实仍然保存 → 如何查询与继续。不要用一句“重试即可”代替状态判断。

## 设计段落

一段回答一个主要问题，但不按固定句数切段。有关联的原因、机制和结果应放在一起。下面这组段落体现的是承接方式：

> 上下文长度有限，任务较长时，需要整理较早的历史，并保留后续执行所需的信息。压缩完成后保存的记录，称为上下文检查点。
>
> 假设检查点覆盖到消息 `m4`。恢复时先加载检查点，再从 `m5` 开始追加。因此，检查点除了保存整理后的历史，还需要保存覆盖位置。

第一段定义做法，第二段用数据解释为何需要这个字段。读者可以顺着机制往下走。

避免连续几段只重复“需要考虑”“值得关注”。讨论恢复时，应进一步说明：运行中的命令继续查询、已结束的命令取回退出码、暂时无法确认的操作保留未知状态。

列表用于并列字段、互斥情况或执行步骤；表格用于需要横向对应的记录与职责。原因和推导仍用段落解释。不要把文章全部写成列表，也不要把表格做成手机上无法阅读的宽矩阵。

## 用语与技术密度

面对的是不熟悉这一实现、但愿意理解技术的读者。解释必要术语，使用真实的对象、参数和例子，语气保持正常交流。

| 含糊或刻意的表达 | 展开为具体机制 |
| --- | --- |
| “平台必须守住自己的事实。” | “素材服务保存任务编号、费用和结果；恢复时按原编号查询，避免重复创建任务。” |
| “不是换一个模型那么简单。” | “切换模型时，需要核对工具参数、调用结果的关联方式，以及上下文与缓存条件。” |
| “接下来讲一个非常关键的点，先记住这句话。” | 直接说明该对象或规则，例如“检查点必须同时保存历史内容和覆盖位置。” |
| “实现可靠的恢复闭环。” | 写清恢复读取哪些记录、如何确认原操作，以及状态未知时如何处理。 |

这些例子用于识别表达问题，不是禁词表。已有专业术语可以使用，但要给出它在本文中的准确含义。

删减时优先去掉重复结论、泛泛感想和多次预告。保留对象定义、必要字段、接口行为、失败条件和具体处理；读不懂实现时，继续补解释，不能只为了缩短篇幅删细节。

代码放在它能帮助理解接口、字段或算法的位置，摘录与当前问题有关的部分，并解释其作用。示意代码、示意表结构和未实施方案要标明，不能伪装成现有实现。

## 事实和实践

- 现有实现以当前源码、配置或可核验记录为依据；历史文章明确当时的时间范围。
- 实际案例、一般设计方法和参考架构分别表述。提出一种可用做法，不等于项目已经采用。
- 一个失败案例可以解释机制，不能直接证明整体成功率、成本或某个模型的能力。
- 外部产品接口和版本细节按当前任务核实，引用能够直接支持表述的官方资料。文风调整不要顺便改写未经核实的技术事实。
- 结尾可以给出适用条件、比较结果或下一步验证内容；没有必要再重复一遍抽象的“经验与启示”。
