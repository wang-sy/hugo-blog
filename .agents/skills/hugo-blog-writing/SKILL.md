# Hugo 技术博客写作

本项目以早期 LevelDB 系列为主要风格参照：从具体问题讲到对象、数据结构、操作过程和特殊情况，图和正文共同解释实现。让第一次接触该实现的读者能够读懂，同时保留必要的技术细节。

用户当前要求优先。根据修改范围使用本 skill：只改标题时直接修改标题；重写文章时才重新组织章节与配图。

## 先确定写什么

- 阅读目标文章及其相关实现，区分已有事实、历史状态、设计建议和示意例子。
- 新写或大幅改写时，按 [行文与段落](references/writing-style.md) 选择一篇 LevelDB 文章，阅读与当前任务相近的章节。参考讲解方式，不机械套用相同大纲。
- 标题直接说明技术对象和讨论范围。读者应能从标题判断文章讲什么，避免只写经历、感想或含糊的“演进”。
- 保留用户提供的实践和具体问题。未核实的效果、性能数字、迁移完成状态不能补写成事实。

## 把实现讲清楚

- 先说明对象是什么、有什么接口或保存哪些数据，再介绍操作如何执行。术语在第一次承担解释作用时说明。
- 一段推进一个问题。上一段介绍的限制，引出下一段的数据结构、接口或处理方式；减少重复铺垫和段末感想。
- 讨论存储时交代内容、位置、写入时机和读取用途；讨论调用时交代发起方、接收方、输入、返回值和后续动作。只写“持久化”“调用工具”“支持恢复”还不够。
- 用一个具体输入贯穿流程。字段、编号和状态在图文中保持一致，特殊情况说明触发条件与实际处理。
- 保留充分展开的篇幅。通过分节、示例、字段图、流程图和必要的表格降低阅读负担，不把正文压成要点摘要。
- 语气直接、平实，承认读者不熟悉实现即可。避免训话、刻意浅白的类比、夸张反问，以及反复拔高为“工程哲学”。详见 [行文与段落](references/writing-style.md)。

## 让图承担解释工作

画图前先确定它要解释的关系：字段布局、包含关系、调用顺序、状态变化或恢复过程。正文介绍问题后放图，图后解释读图所需的字段和例子。

按 [SVG 配图规范](references/svg-style.md) 绘制可编辑 SVG：白底、细黑线、简洁方框，少量颜色区分数据或状态。标题与长篇解释留在正文，图中只放结构、标注和必要的图例。

可按需要从以下模板开始，替换其中的业务对象与关系：

- [消息与检查点](assets/message-checkpoint.svg)：字段横排、记录分组、覆盖范围与引用关系。
- [命令执行会话](assets/command-session.svg)：参与方、时间顺序、调用参数和返回状态。
- [沙箱运行结构](assets/sandbox-runtime.svg)：部署边界、包含关系及进出环境的调用。

模板中的 Agent 例子只是布局示例，不是其他文章的事实来源。

## 写入和检查

使用本项目现有的 Markdown、front matter、图片 shortcode 和 LoveIt 版式，按 [Hugo 写入与预览](references/hugo-workflow.md) 操作。文章放入 `content/posts/`，正式配图放入 `static/images/`，不另外制作网页。

新文章默认保留草稿状态；修改旧文保留原发布状态、日期和地址，除非用户要求改变。沿用本次任务已有的有效授权，skill 本身不扩大仓库或发布权限。

检查与改动相称：

- 标题修改：核对标题是否准确，并确认生成页面与首页显示一致。
- 正文修改：核对章节衔接、技术事实、术语和图文对应关系。
- 新增或重画配图：实际渲染 SVG，检查文字、边界、箭头和字号，再在原生文章中查看。
- 新文章或大幅改写：构建 Hugo，查看桌面和手机排版、表格、图片加载与放大。

交付时给出文章或预览入口，简要说明修改及验证结果。不要把整篇文章重复粘贴进对话。
