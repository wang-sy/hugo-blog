最开始，我们这条生成链路的核心就是两个服务：一个 Gateway，一个 Runtime。

Gateway 接用户请求，处理项目相关的接口，再通过 RPC 把执行交给 Runtime。Runtime 跑 Agent，调模型和工具，维护执行状态，把过程和结果传回来。项目、素材、用户以及各种外部依赖，很多都围着这两个服务接。

当时这么做很自然。产品还在快速变化，先把一条生成链路跑通，比提前设计十几个服务更重要。两边接口对齐，部署两个应用，就能开始验证。

但今天再看，前面有 NLB 和 Nginx，有按业务划分的 Gateway，也有面向移动端的 WAP；后面有项目服务、调度、Runtime 和其他领域服务。旁边还长出了一整套环境管理、发布、监控、日志和告警。

这些东西是怎么一步步长出来的？我觉得值得讲的，是每次拆开一个边界以后，我们又必须补上什么。

**服务拆开了，调用关系就要有人管理；允许不同版本同时跑，环境选择就要贯穿整条链；发布不再只有两个应用，制品、目标和运行结果就必须能对得上。** 后面的研发平台，就是沿着这些问题做出来的。

## 1. 两个服务的时候，我们到底把什么放在了一起

早期 Gateway 已经通过 Kitex RPC 调 Runtime。Runtime 也已经有任务状态、事件传递，以及运行、工具调用和错误指标。理解后面的演进，要从这个起点出发。

那时的简单，主要体现在边界和绑定方式上。

Gateway 知道 Runtime 的地址，直接调用。CI 根据提交来源，选择一组固定应用：某个人的 Gateway 配某个人的 Runtime，共享开发环境再有自己的一组。构建镜像以后，流水线找到对应的云应用，更新镜像，等待部署结束。

服务只有两个，这套方式很直观。调试时知道自己连的是谁，发布时知道要更新哪两个应用。为了联调维护几组地址和应用映射，也还能接受。

问题出在 Gateway 承担的事情越来越多。它既要理解客户端请求，又要处理项目相关逻辑，还要衔接任务、资产和外部系统。Runtime 则围着执行过程继续变复杂。一次产品改动，经常同时碰到入口、项目状态和执行过程。

回头看，当时真正需要拆开的，是三种不同的变化：**客户端协议怎么变，项目状态由谁维护，一次长任务怎样被安排和执行。** 它们挤在一起时，接口最少；它们开始各自演进时，修改和发布就会互相牵扯。

这也是我们没有一开始就拆很多服务的原因。先把业务跑起来，才能看清哪些东西真的在一起变化，哪些只是暂时写在了一起。

## 2. 第一轮拆分：项目状态和任务调度离开入口

接下来比较关键的一步，是把项目管理和任务调度从原来的大入口里抽出来。

项目服务接住项目、版本等业务状态；Dispatcher 接住任务的提交、排队和分发；Runtime 继续负责 Agent 执行。Gateway 保留客户端接入和必要的业务编排，通过 RPC 使用这些能力。

这样，入口校验请求以后，由调度服务组织项目创建和首轮执行，通过 RPC 推动 Runtime 工作；需要异步处理的事件和后续工作则进入队列。项目对象、任务执行和客户端连接，开始有各自的生命周期。

这个拆分的价值，落在几个很具体的地方。

项目状态可以被不同入口复用。以后增加移动端，不需要让移动端依附于原来那套大 Gateway 的全部接口，也不需要再维护一份项目模型。

排队和调度有了自己的位置。任务什么时候被领取、积压在哪里、执行服务能不能接住，可以围绕调度这一层观察和处理。

Runtime 可以继续围着执行能力演进。客户端换一种返回格式，不应该要求它跟着理解一整套页面交互；用户断开连接，也不应该顺手把正在运行的任务删掉。

当然，这次拆分没有免费午餐。原来两台应用之间的一次 RPC，变成了入口、项目、调度、执行之间的多次协作。要理解一个请求，开始需要跨服务看；要验证一套新逻辑，开始需要一组匹配的版本。

**灰度的问题，就是从这里变复杂的。** 以前把请求送进个人 Gateway，大致就知道后面会发生什么。现在个人 Gateway 后面可能连着共享调度，共享调度再把消息交给另一套 Runtime。入口看着是自己的，真正执行的却未必是。

## 3. 灰度选路，我们前后调整了四轮

这里说的灰度，主要是按环境标记定向验证，以及预发布环境的选择。我们这条演进线里，核心问题是让同一套新逻辑稳定地接到目标请求。按百分比逐步放大正式流量，是另一类发布策略。

如果按“请求究竟怎样找到对应版本”来分，可以拆成四轮。它们有一段时间会并存，也会逐步迁移，不能理解成四次整站推倒重来。

{{< image src="/images/rd-platform-evolution/18-gray-four-designs.svg" alt="图 2：灰度从固定地址表，演进到贯穿调用链的请求上下文" caption="图 2：灰度从固定地址表，演进到贯穿调用链的请求上下文" width="1200" height="1262" >}}

### 第一轮：固定应用，固定地址，Nginx 维护映射

最早是给人配环境。CI 把代码发到这个人固定的应用，请求带上环境标记，Nginx 再把标记翻译成某个 NLB 地址或端口。Gateway 后面用配置好的地址连接 Runtime。

这里的 NLB 是当时 Nginx 选择的上游地址。后来基础设施迁移以后，NLB 和 Nginx 的连接关系也变了，不能拿今天的拓扑去套早期方案。

这个版本的优势就是简单。改一条映射，就能明确地把一类请求送到某个应用。预发布和正式环境，也可以通过不同的上游目标分开。

但它要同时维护几份对应关系：人对应哪个应用，环境标记对应哪个地址和端口，Gateway 又对应哪个 Runtime。人多了、服务多了，每加一套环境，都要把这些表一起补齐。

问题开始从“地址能不能连上”，变成“几份配置有没有一起改对”。

### 第二轮：按命名空间找服务，找不到再用共享环境

接下来，我们把一部分地址选择交给服务发现。调用方先在当前命名空间查找同名服务，确实不存在时，再按规则去共享环境找。

这样调用方不再保存每个实例的地址。服务部署到哪里、实例怎么换，交给运行环境和 DNS 维护；调用方围绕稳定的服务名调用。

共享回退也有实际意义。个人只改一个服务时，不必为了这次验证，把所有依赖都复制一遍。

不过，**这时环境身份和命名空间绑得比较紧。** 服务多起来以后，我们希望在同一个开发命名空间里放多组实例，也希望复用没有改动的服务。只根据“调用方进程住在哪个命名空间”选下游，就不够细了。

### 第三轮：同一命名空间，用服务名前缀区分环境

于是环境标记开始进入服务名。同一组个人实例使用同一个前缀，服务发现先找带这个前缀的目标，再按策略找共享版本。Nginx 也可以从环境标记推导服务名，不必继续维护一张“每个人对应哪个端口”的表。

发布时，CI 还要把环境身份写进实例配置，让这个进程知道自己属于哪一组。调度队列也逐步从按命名空间划分，转向按这份环境身份区分。

这一步降低了维护固定地址表的成本，但又露出一个问题：**进程自己的环境，不总是这次请求想去的环境。**

比如共享 Gateway 可以接多个人的请求。如果后面的服务发现只读取 Gateway 进程自己的配置，这些请求最后仍然会被送到共享下游。只给服务起一个带前缀的名字，并不能让环境选择自动穿过整条调用链。

### 第四轮：环境成为请求上下文，继续穿过 RPC 和消息队列

后面才逐渐形成今天这套做法：HTTP 入口识别环境选择，放进请求上下文；标准 RPC 客户端把它传给下游；生产消息时写进消息属性，消费时再恢复到上下文。

每一跳都根据这次请求的环境来选目标。服务发现的缓存也要带上这份环境信息，否则两个人调用同一个逻辑服务名，仍可能复用到同一份错误结果。

这时，共享 Gateway 就可以接住一条个人请求，再把它送到个人 Dispatcher 和 Runtime。有没有个人 Gateway，和后面的执行应该去哪一组，成为两次独立、但使用同一环境上下文的选择。

{{< image src="/images/rd-platform-evolution/19-routing-context.svg" alt="图 3：共享入口如何把个人请求交给对应的 RPC 与异步执行链" caption="图 3：共享入口如何把个人请求交给对应的 RPC 与异步执行链" width="1200" height="1084" >}}

*这里画的是开发联调链路。环境选择负责路由，身份认证和操作权限仍然单独校验。*

做到这里，还得把回退策略说清楚。我们给依赖区分了优先个人、必须个人、仅共享等策略。普通依赖可以按约定复用；关键调度和执行必须命中同一组实例，缺少就明确失败。

入口允许回退时，也只把明确的 DNS 不存在当成“这组服务没部署”。DNS 超时、上游连接失败或者应用返回错误，都不能随手解释成“换共享版本再试一下”。否则新版本出错，系统却拿旧版本接住，联调结果会把问题藏起来。

这四轮调整，改变的是环境信息的归属：一开始它写在运维配置里，后来写在部署位置和进程身份里，最后必须跟着请求和任务走。**当一个进程要为多套验证环境服务时，环境就不能只是一份启动参数。**

## 4. 选路有了，为什么个人环境还是会跑不通

路由变严格以后，发布范围也得跟着改。

一次生成要经过入口、调度、Runtime。如果只改了入口，流水线按代码差异生成任务，就可能只部署入口。入口已经是新版本，后面两个个人实例却根本不存在。

这时候不能再靠静默回退把请求接过去。我们给这条关键链加了发布组：命中相关改动时，把需要的调度和执行实例一起带上。构建可以并行；部署则先 Runtime，再 Dispatcher，最后入口。

{{< image src="/images/rd-platform-evolution/01-overview.svg" alt="图 4：代码依赖决定构建范围，运行依赖还要求补齐关键发布组" caption="图 4：代码依赖决定构建范围，运行依赖还要求补齐关键发布组" width="1200" height="974" >}}

*发布组保证按约定准备链路，不提供跨服务事务，也不代表所有数据库都随之隔离。*

这个问题让我对“只发改过的服务”有了更具体的理解。它适合减少构建和发布工作，但前提是目标环境已经有完整、兼容的依赖。刚创建的个人环境，显然不一定满足这个前提。

环境本身也从按人常驻，逐步变成按功能分支创建。一个人同时做几件事时，用人名只能表示操作者，无法清楚表达正在验证哪套代码。分支更接近这次改动的实际寿命：打开变更时准备环境，更新代码时继续发布，合并、关闭或到期后回收。

但从固定应用转成临时资源，又多出两个问题。

第一，哪些东西可以复制。个人链路使用内部 Service，复用允许共享的依赖；不能把共享入口的 NLB 绑定也原样克隆，否则个人实例可能误接到共享流量。数据库和外部资源也不能因为“环境独立”几个字就默认复制。

第二，名字可以复用，资源身份不能混用。一条旧回收任务晚到，不能把同名的新环境删掉。所以回收要先关闭这代环境、阻止新的发布，等待正在执行的操作退出，再按精确资源身份删除。重新创建时是一代新的资源。

{{< image src="/images/rd-platform-evolution/10-lifecycle.svg" alt="图 5：旧环境回收与新环境创建，通过代次和资源身份分开" caption="图 5：旧环境回收与新环境创建，通过代次和资源身份分开" width="1200" height="980" >}}

按分支创建和回收，解决的是资源属于谁、何时存在的问题。前面四轮灰度解决的是请求去哪的问题。两边最后使用同一份分支环境身份，才算接到了一起。

## 5. Gateway 继续拆，入口才变成今天这样

项目和执行链拆出去以后，原来的大 Gateway 还在承接很多不同业务。后续我们继续按业务划分接入服务，把项目、用户、支付、内容等接口逐步迁出去。

这个过程也需要一个稳定入口。外部调用方不可能跟着每次服务拆分改一遍接入方式，所以 Nginx 按路径把请求交给新旧 Gateway。一个领域迁完，再移走旧路由，最后才能撤掉原来的大入口。

迁移期间保留旧实现很方便，但错误回退要收紧。新 Gateway 返回错误时，如果自动转回旧 Gateway，可能把新实现的问题掩盖掉；涉及写操作时，也不能假设换一个上游重试总是安全。迁移完成以后，旧入口和过渡回退都需要退出。

到现在，主要的请求链路才是下面这样。

{{< image src="/images/rd-platform-evolution/15-ingress-chain.svg" alt="图 6：当前 NLB、Nginx、Gateway 与 WAP，以及内部 RPC 的职责" caption="图 6：当前 NLB、Nginx、Gateway 与 WAP，以及内部 RPC 的职责" width="1200" height="1220" >}}

*图从业务 API 的 NLB 展开；域名前的代理和 TLS 终止配置不在这里统一假设。鉴权是 Nginx 发起的子请求分支。*

NLB 负责把连接交给入口实例。Nginx 负责 HTTP 路由、协议升级和鉴权衔接。Gateway 负责对应业务的客户端协议与编排，内部服务通过 RPC 提供项目状态、调度和执行能力。

迁到 Kubernetes 时，我们保留了外部入口的地址和监听，再把后端接到由控制器维护的 Pod 集合。这里有一个容易漏的细节：原托管平台控制的服务器组，不能直接假设可以交给新的集群控制器接管。入口地址可以延续，后端资源的管理归属仍然要重新接好。

WAP 则来自另一种变化：移动端需要更收敛的创建和对话协议。它和普通 Gateway 并列，下面复用项目、版本、文件以及调度执行能力。没有必要为了手机端再复制一份项目状态。

{{< image src="/images/rd-platform-evolution/16-client-rpc-lifecycle.svg" alt="图 7：移动端 HTTP、WebSocket 和内部 RPC，分别承接不同生命周期" caption="图 7：移动端 HTTP、WebSocket 和内部 RPC，分别承接不同生命周期" width="1200" height="1124" >}}

一次创建请求通过 HTTP 返回项目对象；之后 WebSocket 连接项目，WAP 核对访问权限，再桥接内部双向 RPC 流，把命令和事件转换成移动端协议。用户关掉页面，结束的是这条观察连接；停止生成则需要明确指向当前轮次的终止命令。

回头看，这两种拆分的理由不同。按领域拆 Gateway，是让不同业务的接口和发布少一些牵扯；增加 WAP，是让不同客户端独立演进。它们都继续复用业务状态的所有者，避免每拆一个入口，就多出一份需要同步的数据。

## 6. 监控：从 Runtime 自己报，到整条链可以一起看

最早的 Runtime 已经在报运行、工具调用、RPC 和错误指标，Gateway 也有自己的请求监控。后来服务一多，首先遇到的是口径和接入方式不一致。

如果每个服务都自己写一次请求计数、耗时统计和上报循环，最后就会出现同一个概念有不同标签、不同分母、不同聚合方式。图能画出来，横向比较却未必成立。

我们先把重复部分收进公共组件。Kitex 在标准中间件里记录调用量、错误、耗时和并发；Hertz 的 HTTP 入口使用统一采集方式；服务定期把指标送到托管 Prometheus 的 PushGateway，再由 Prometheus 保存和查询，Grafana 展示和计算规则。

{{< image src="/images/rd-platform-evolution/20-metrics-collection.svg" alt="图 8：监控采集逐步统一，平台通过服务和部署目标绑定查询范围" caption="图 8：监控采集逐步统一，平台通过服务和部署目标绑定查询范围" width="1200" height="1110" >}}

这里有两层建设，缺一层都不行。

一层是服务确实在采集。RPC 中间件、HTTP 中间件、队列和业务埋点，都得产生正确的样本。另一层是这些样本能被统一发现和使用：服务目录知道它提供哪些能力，对应哪套监控模板，实际部署在哪个目标。

后来面板和规则开始从服务清单、能力和模板生成，研发平台再把部署目标与查询范围接起来。新服务不用从头手抄一份面板，但勾选一个能力也不会凭空长出监控数据。采集没接上，就应该显示缺少数据。

**统一采集之后，还要统一“成功”是什么意思。**

HTTP 返回成功，只能说明入口接收了请求；RPC 成功，只能说明这一次调用完成。生成任务可能还在排队，也可能在某次工具调用后失败。我们把队列积压和等待、调用错误与重试、最终任务结果分开观察。

{{< image src="/images/rd-platform-evolution/04-outcomes.svg" alt="图 9：入口成功、调用成功和任务最终成功，使用不同的统计口径" caption="图 9：入口成功、调用成功和任务最终成功，使用不同的统计口径" width="1200" height="868" >}}

用户关掉页面、主动停止任务，和执行器崩溃也不能混成一种系统错误。任务最终失败率按任务结果统计，一次任务中的多次重试留在调用指标里。否则模型调用重试多了，图上就像用户失败了好几次；入口一直返回 200，又可能让最终失败完全被掩盖。

再往后，我们把数据库、Redis 等依赖也接进来。标准客户端的插件和 Hook 记录谁在调用、耗时和错误；云监控提供对应实例的 CPU、内存、连接数和 I/O。先对齐资源身份和时间窗口，再判断慢在调用方、连接池还是资源本身。

{{< image src="/images/rd-platform-evolution/05-infrastructure.svg" alt="图 10：应用侧调用指标与云资源指标，通过资源身份关联" caption="图 10：应用侧调用指标与云资源指标，通过资源身份关联" width="1200" height="818" >}}

发布目标也会影响监控准确性。预发布和正式环境可能都使用生产配置，指标里的环境标签未必足以区分；查询还要约束实际部署实例。反过来，共享 Gateway 接一条个人请求时，进程所属环境与请求选择的环境也不同，不能为了灰度就把所有基础指标都改成请求环境。

告警同样沿着这个方向收敛：Grafana 负责计算规则，平台维护事件状态、分级和通知节奏，既有消息服务负责实际发送。请求错误、队列卡住、最终任务失败和资源饱和分别定义条件，避免同一件事在每一层都无差别地轰炸。

我们保留 Prometheus 和 Grafana 做它们擅长的事。平台主要补上的是：这张图属于哪个服务、哪次部署、哪个实例，以及异常应该进入谁的处理范围。

## 7. 日志：业务服务和 Nginx，走两条采集通道

早期日志更多由各个进程自己组织：Runtime 有自己的输出和上下文字段，Gateway 有自己的文件与轮转配置。服务少时，知道去哪个应用看，问题还不大。

拆开以后，一次操作要经过多个进程，再逐个翻就很难受。日志建设首先要解决两个问题：怎样汇到一起，以及汇到一起之后怎样知道它属于哪次请求、哪个实例。

业务服务这条线，后来收敛到了公共日志库。业务代码通过统一接口写日志，公共库负责补上服务、运行环境和调用位置，保留请求、任务等上下文字段，再由 SLS 后端异步批量发送。标准输出仍然可以保留，用于进程启动和现场排查。

{{< image src="/images/rd-platform-evolution/21-log-collection.svg" alt="图 11：业务日志通过公共库写入 SLS，Nginx 日志由采集进程读取后上报" caption="图 11：业务日志通过公共库写入 SLS，Nginx 日志由采集进程读取后上报" width="1200" height="1194" >}}

Nginx 是另一条线。它不会直接调用 Go 的公共日志接口，所以我们把访问日志整理成结构化 JSON，再增加一个随入口镜像运行的采集进程，读取访问日志和错误日志，解析字段、处理需要脱敏的内容，批量写入 SLS。

因此，业务日志主要是应用通过 SDK 上报；入口日志则是 Nginx 先写文件，由采集进程读取后上报。入口日志里的请求标识、状态、上游和耗时，用来判断请求到了哪一跳；业务日志里的请求、任务和执行标识，再帮助我们继续往后查。

这个过程里还补过一些容易漏的来源。比如消息队列 SDK 自己打出的警告，如果仍然走独立的输出通道，就可能在业务查询里缺一块。把 SDK 日志接进公共库，才有机会在同一时间窗口里看到它和业务异常的关系。

日志集中以后，另一个问题反而更突出：很容易查到很多，却不一定查对了。

预发布和正式环境共用一份生产配置时，只筛一个环境标签，会混入两套实例。平台后来把服务的目标声明、完整实例范围和时间窗口一起带进查询，返回后再核对归属；翻页也固定在同一个时间窗口里，避免第一页和第二页实际上查的是两批东西。

{{< image src="/images/rd-platform-evolution/06-logs.svg" alt="图 12：从发布目标推导日志范围，避免同配置的不同环境混查" caption="图 12：从发布目标推导日志范围，避免同配置的不同环境混查" width="1200" height="990" >}}

**日志写出去、SLS 收到、字段建好索引、查询能命中，是四个不同环节。** 接好了 SDK，不代表页面一定能查到；页面没有结果，也不代表服务没报错。发布验收时，需要拿同一个请求标识确认整条查询链能够找到对应记录。

异步采集还会遇到进程退出、发送失败、缓冲积压等情况。它适合排障和观察，任务最终结果仍然要以业务持久状态为准。把日志集中起来，也不等于所有调用已经具备完整的分布式追踪。

## 8. 上线绑定：从 CI 选两个应用，到绑定一整套运行关系

最早的发布绑定，写在 CI 里：根据提交来源和环境，选固定应用，推镜像，更新应用。规模小时，这张映射表本身就是发布系统。

服务拆开以后，构建范围先变复杂了。哪些模块改了，共享代码影响了哪些调用方，哪些服务虽然没改却是个人环境必须存在的依赖，都要被展开。动态流水线解决代码依赖，发布组补运行依赖。

但真正需要从 CI 里拿出来的，是“这个制品到底允许更新哪个运行目标”。页面、CLI 和自动化也开始发起发布以后，再让每个入口各自拼集群名、应用名和环境变量，迟早会产生不一致。

后来我们把发布目标和执行收进研发平台。CI 交出可以核验来源的构建结果，平台登记制品，解析目标，保存发布操作，由持久 Worker 执行。CI、页面和 CLI 都围绕同一份操作记录查进度。

{{< image src="/images/rd-platform-evolution/22-release-bindings.svg" alt="图 13：发布从固定应用映射，演进到制品、目标、路由与观测的共同绑定" caption="图 13：发布从固定应用映射，演进到制品、目标、路由与观测的共同绑定" width="1200" height="1324" >}}

具体说，上线现在要接好下面几组关系。

| 要绑定的关系 | 绑定的内容 | 少了以后会怎样 |
| --- | --- | --- |
| 代码 → 制品 | 提交、真实构建任务、镜像 digest 和构建来源 | 只能知道标签，无法确认到底运行哪份构建 |
| 制品 → 发布目标 | 逻辑服务、目标环境、部署对象和配置身份 | 同一份镜像可能被发到错误对象，或配上不匹配的配置 |
| 发布目标 → 流量 | Service 选择器、实例标签；入口还涉及 NLB 监听与后端集合 | Pod 正常启动，却接不到目标流量，或接错流量 |
| 运行实例 → 观测范围 | 服务、环境、实例与日志字段、指标模板的对应关系 | 发完以后看到旧实例，或把预发布和正式结果混在一起 |
| 发布操作 → 验收结果 | 本次实际目标、制品、执行进度和功能检查 | 流水线成功了，却说不清用户链路是否真的可用 |

镜像用 digest 固定，是为了让构建结果有明确身份。对于声明了预发布的服务，晋级正式环境要核对同一制品及兼容配置；不能测试一份，重新构建另一份后就假设它们一样。没有预发布声明的服务，则走自己明确声明的发布流程。

配置同样要有身份。有的服务把环境配置随镜像封装，有的仍然引用外部配置；无论采用哪一种，发布记录都得能回答这次用了哪份配置。仅仅说“都是生产环境”，信息不够。

流量绑定也不是把 Service 创建出来就完事。Service 的选择器得匹配这次部署的实例，NLB 的后端管理要交给正确的控制器，个人服务不能带上共享入口的外部负载均衡绑定。这些都是运行目标的组成部分，不能留给临时脚本随意拼接。

最后是执行状态。发布请求超时，可能只是调用方没有拿到响应，部署动作仍在继续。重试时先查原操作，核对目标和制品，再决定后续动作；直接新建一份发布，可能让两次操作同时更新同一个目标。

{{< image src="/images/rd-platform-evolution/09-unknown-result.svg" alt="图 14：结果未知时查询原发布操作，避免重试变成另一次部署" caption="图 14：结果未知时查询原发布操作，避免重试变成另一次部署" width="1200" height="1000" >}}

平台为此承担了新的复杂度：持久任务、互斥与租约、恢复执行，以及自身的可用性。它不在用户业务请求的转发链上，但新的发布依赖它正常工作。把执行权收进来，就必须同时接住恢复和排障责任。

## 9. 这条演进里，我们真正改变了什么判断

现在再回头看，两个服务时最重要的是快：把产品跑通，把执行链跑通，尽快验证想法。当时的固定地址、固定应用和简单 CI，和当时的问题是匹配的。

服务多了以后，我们逐步发现，拆分只是起点。每多一个独立变化的服务，就多一份环境选择、多一个发布目标、多一段需要解释的运行结果。没有相应的治理，服务数量会直接变成联调和排障负担。

所以几条线其实一直在相互推动。

调度从入口拆出去以后，环境要跟着异步消息走；关键执行链要求同环境以后，发布就必须成组准备依赖；实例可以按分支创建以后，监控和日志就不能再依赖几个人记住固定应用；发布迁到平台以后，服务身份、制品身份和资源身份又必须被明确保存。

这些设计最后都要落到一次具体的验证上。打开某条分支环境，发起生成，确认入口选择了正确的后端；从 RPC 和消息继续确认调度与 Runtime 没有串环境；看到任务最终产出；再用同一个请求或任务标识查到入口和业务日志，并确认监控指向这次部署的实例。

到这一步，才能说明这套新逻辑在目标环境里工作。CI 变绿、Pod Ready、HTTP 返回 200，各自只能回答其中一段。

我现在更愿意用这个标准判断要不要增加一层架构：**它接住了哪一种已经出现的变化，谁从此对这件事负责，出问题时能不能明确找到它。** 能回答清楚，再付出一次转发、一份状态和一套部署的成本；回答不清楚，就先不要急着拆。
